# 0008. Contact form definition in D1 with immutable field ids

- Status: accepted
- Date: 2026-10-22

## Context

The contact form had fixed fields (name, email, company, phone, category,
message), one column each in `submissions`. Categories came from the
`contact.categories` option in `src/worker.ts`, so changing the form meant a
code change, a build, and a deploy. The people who run a goodnight-web site
are often not engineers.

Making the fields editable raises three problems:

- **Storage.** A column per field would need a schema migration for every
  edit, and migrations reach a site only with a package release.
- **History.** Labels change and fields come and go. An inquiry from last
  month must still read as the visitor saw the form.
- **Mixing.** If a field is removed and a new one with the same label is
  added later, their answers must not end up in one column of the list or
  the CSV.

## Decision

- The definition is data in D1. `form_definitions` has one row per saved
  version (`version`, `definition` JSON, `created_at`, `created_by`,
  `restored_from`). The highest version is the current form. Triggers refuse
  `UPDATE` and `DELETE`, so a version never changes after it is saved.
- Every field has an immutable id (`^f_[a-z0-9]{1,32}$`) generated by the
  server. Clients send new fields without an id; an id that no version ever
  had is refused. Option values are generated the same way.
- Every edit (label, type, option, order, setting) is a new version. A type
  can change only within the same value shape (text types, single choice,
  multiple choice, number, date).
- Removing a field archives it: the definition keeps an `archived` list with
  the last known settings and `lastVersion`. Archived ids are never reused;
  putting a field back keeps its id. Restoring an older version saves its
  fields as a new version.
- `submissions.fields` holds the values as JSON keyed by field id, and
  `submissions.form_version` the version they were validated against. Email
  stays a real, required column; consent, honeypot, and Turnstile stay fixed.
- `POST /api/contact` validates `fields` with a zod schema built from the
  stored current version, never from a definition sent by the client.
  Unknown keys are refused; a stale `formVersion` gets 409 `form_outdated`.
- The detail view labels each inquiry with its own version. The list shows
  the current version's fields. The CSV has a column per field id ever used.
  The list has no keyword search; filters are status, version, and the
  option of a select or radio field.
- Slack messages carry no field values (count, received time, admin link).

## Alternatives considered

- **A column per field.** Rejected: a migration per edit, and migrations ship
  only with releases.
- **Keys chosen by the admin (`company`, `budget`).** Rejected: a key reused
  after a delete would mix old and new answers. Generated ids cannot be
  reused.
- **A label snapshot on every submission.** Not needed: versions are
  immutable and never deleted, so `form_version` points at a snapshot that
  cannot change. A per-row copy would only add bytes to every inquiry.
- **Keyword search over `fields`.** Rejected for now: `LIKE` over every value
  scans the table, and a full-text index would have to follow every form
  edit. Filters and the CSV export cover the common needs.
- **Sorting by form fields.** Rejected: each field would sort through
  `json_extract()` with its own plan; the fixed columns are enough.

## Consequences

- Admins change the form without a deploy, and the starter renders it at
  runtime from `GET /api/contact/form`.
- Old inquiries keep their labels; archived values are shown as "from
  version N / archived" in the detail.
- `form_definitions` grows by one small row per save. Nothing prunes it, so
  the history is complete.
- Migration `0004` seeds version 1 with fixed ids (`f_name`, `f_company`,
  `f_phone`, `f_category`, `f_message`) and copies the old columns into
  `fields`; `0005` drops the old columns. This drop is the one non-additive
  schema change, made before the first release.
- If a later migration rebuilds `form_definitions`, it must create both
  triggers again (`AGENTS.md`).
