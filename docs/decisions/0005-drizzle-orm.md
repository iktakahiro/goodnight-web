# 0005. Drizzle ORM for D1 access and migrations

- Status: accepted
- Date: 2026-10-22
- Updates: [0002](0002-migrations-from-package.md) (how migration files are
  written; how they ship and run is unchanged)

## Context

Until now the server package used D1's `prepare()` with hand-written SQL.
Values were bound, but the admin list put `LIMIT` and `OFFSET` into the SQL
text after the route checked them as integers. That was safe only as long as
every caller kept the check. The migrations were written by hand, except the
Better Auth tables, which came from the Better Auth CLI as SQL.

Goals:

- SQL injection safety by construction: app code cannot put input into SQL
  text.
- One schema in TypeScript for the app tables and the Better Auth tables, and
  one migration history generated from it.
- The deploy path for users stays the same: `wrangler d1 migrations apply DB`
  with `migrations_dir` inside `node_modules`.

Nothing was published when this was decided, so the old migration history
(`0001_better_auth`, `0002_submissions_settings`, `0003_setup_closed`) was
replaced by a new one. `@goodnight-web/server` 0.1.0 has been published on
npm since 2026-10-23, so its migrations are released and must not change.

## Versions

All versions are older than the 48-hour release-age gate.

| Package                               | Version | Published  |
| ------------------------------------- | ------- | ---------- |
| `drizzle-orm`                         | 0.45.4  | 2026-10-08 |
| `drizzle-kit`                         | 0.31.11 | 2026-09-21 |
| `better-auth`, `@better-auth/passkey` | 1.7.11  |            |
| `wrangler`                            | 4.151.2 |            |

Better Auth 1.7.11 declares `drizzle-orm ^0.45.2` and `drizzle-kit >=0.31.4`
as optional peers. Its Drizzle adapter (`better-auth/adapters/drizzle`) only
uses transactions for MySQL, so it works on D1, which has no interactive
transactions.

## Decision

- `packages/server/src/db/schema.ts` defines every table: `submissions`,
  `settings`, and the Better Auth tables `user`, `session`, `account`,
  `verification`, `passkey`. The Better Auth part is generated by the Better
  Auth CLI for the Drizzle adapter
  (`bun run auth:schema <tmp>/auth-schema.ts` in `packages/server`, which
  runs the pinned `auth` devDependency) and
  kept in the file unchanged except for TSDoc. Column names are snake_case.
  Better Auth timestamps are integer milliseconds (`timestamp_ms`).
- `packages/server/drizzle.config.ts` (`dialect: 'sqlite'`,
  `out: './migrations'`). `bun run db:generate` runs `drizzle-kit generate`.
  The generated SQL is committed. A released migration is never edited.
- Things drizzle-kit does not model go in custom migrations
  (`drizzle-kit generate --custom --name <name>`): the default settings rows
  (`0001_settings_defaults.sql`) and the trigger that closes setup on the
  first passkey insert (`0002_setup_closed_trigger.sql`). The old backfill
  for sites that already had passkeys is gone: there is no such site.
- Better Auth uses `drizzleAdapter(db, { provider: 'sqlite', schema })` with
  the same Drizzle schema. It is built from the request's `env` and cached
  per isolate as before ([0001](0001-passkey-auth-on-workers.md)). It is
  imported from `better-auth/minimal`, which leaves out Kysely; Kysely is
  only needed for Better Auth's built-in database dialects.
- `getDatabase(env.DB)` in `src/db/database.ts` returns the Drizzle database,
  cached per D1 binding. Every query in app code uses the Drizzle query
  builder. The admin list uses `.limit()` and `.offset()`, which bind both
  values. The route validates `page` (1 to 100,000) and `limit` (1 to 100,
  default 50) with zod: digits only, no sign, exponent, fraction, spaces, or
  leading zeros; anything else is 400.
- Raw SQL only through Drizzle's `sql` template, which binds every
  interpolated value. `sql.raw(`, `.prepare(`, and `$client` are forbidden in
  `packages/server` by `scripts/check-sql.ts`. The allowlist names the test
  helpers (`src/testing/`), test files (`*.test.ts`), and the e2e harness.
  Drizzle's own prepared queries (`query.prepare()`) also match `.prepare(`;
  we accept that, since we do not use them.
- The package ships only the `.sql` files. `migrations/meta/` (drizzle-kit's
  journal and snapshots) stays in the repository and is left out of the
  package (`"!migrations/meta"` in `files`).

## Migrations with wrangler: what we tested

drizzle-kit writes `migrations/NNNN_name.sql` (four digits from `0000`) and
`migrations/meta/_journal.json` plus one snapshot per migration. Wrangler
reads only the `.sql` files at the top of `migrations_dir`, sorted by name,
and records applied files by name in `d1_migrations`. The `meta/` directory
is ignored. drizzle-kit's `--> statement-breakpoint` lines are SQL comments.
In every case below, a file that failed left no changes behind.

All commands ran with the workspace's wrangler 4.151.2 and `--local` only.
The package was packed with `npm pack` and extracted into
`site/node_modules/@goodnight-web/server` (a real directory, as npm
installs it), with `"migrations_dir": "node_modules/@goodnight-web/server/migrations"`.

| Case                                              | Result                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Fresh database, `migrations list` and `apply`     | Lists and applies `0000_initial_schema.sql`, `0001_settings_defaults.sql`, `0002_setup_closed_trigger.sql` in that order. All tables, the trigger, and the two settings rows exist. A second `apply` says "No migrations to apply".                                                              |
| Database at the old state (old 0001–0003 applied) | Wrangler sees three new names and tries `0000_initial_schema.sql`, which fails with "table `account` already exists". Nothing is recorded and nothing changes. Such a database (only local development ones exist) must be recreated: delete `.wrangler/state` and apply again.                  |
| A later generated migration                       | A temporary schema change (one new column) gave `0003_*.sql` with one `ALTER TABLE ... ADD`. Wrangler applied only that file.                                                                                                                                                                    |
| A change that rebuilds `passkey`                  | drizzle-kit rebuilds the table (`CREATE TABLE __new_passkey`, copy, `DROP TABLE passkey`, rename). Rows survive, but the `passkey_closes_setup` trigger is dropped with the old table, without any error.                                                                                        |
| A change that rebuilds `user`                     | Same pattern. drizzle-kit wraps it in `PRAGMA foreign_keys=OFF`, but D1 does not turn foreign keys off inside a migration, so `DROP TABLE user` cascades and **deletes every session and passkey**. Replacing it with `PRAGMA defer_foreign_keys = on` did not help. Admins would be locked out. |
| A rebuild that makes a nullable column NOT NULL   | The copy fails on existing NULLs ("NOT NULL constraint failed"). D1 rolled back the whole file; the migration was not recorded.                                                                                                                                                                  |

Guards in the repository:

- `src/db/migrations.test.ts`: file names are `NNNN_name.sql`, numbered
  without gaps from `0000`, and match the drizzle-kit journal one to one; no
  migration contains `DROP TABLE user`; the trigger exists after all
  migrations. The setup tests also check that setup stays closed after every
  passkey is deleted.
- `bun run db:check` (`scripts/check-migrations.ts`) runs `drizzle-kit
  generate` against a copy of `migrations/` and fails if it would write a new
  file, so a schema change cannot be merged without its SQL.

Rules for schema changes (also in `AGENTS.md`): read the generated SQL before
committing it. If it rebuilds `passkey`, add the `CREATE TRIGGER` statement
from `0002_setup_closed_trigger.sql` to the end of the new file (it is not
released yet, so it may be edited). If it rebuilds `user`, do not commit it;
change the schema so that it needs only `ALTER TABLE ... ADD`, or write a
custom migration that keeps the child rows.

## Logging

`DrizzleQueryError` puts the SQL and the bound values into its message. A
failed contact insert would have logged the visitor's name, address, and
message, and a failed Better Auth write could log an address or a session
token. `safeErrorMessage()` (`src/shared/log-error.ts`) is the one place that
turns an error into log text. For a query error anywhere in the `cause` chain
it keeps only the database's own error message (for example "no such table:
submissions"), and it redacts query text that another error copied into its
message. Every log call in the server passes errors through it:

- Route code and the app's `onError` log `safeErrorMessage(error)`, never the
  error object.
- Better Auth gets a `logger.log` that redacts the message and drops every
  argument except error messages passed through the same function.
- Better Auth runs with `onAPIError.throw`. Without it, its HTTP router
  (Better Call) logs a non-API error object with `console.error`, bypassing
  the logger. The rethrown error reaches the app's `onError` and answers 500
  `server_error`.
- Better Auth runs with `advanced.database.joins`, so a session and its user
  load in one relational query. The fallback runs a second query and logs a
  failure with `console.error`, bound values included.

Tests drop a table, call the HTTP endpoints (contact, setup, passkey
registration, session reads, the admin API), and check with `Bun.inspect`,
which shows an error's message and properties, that the logs contain no
submitted values, address, user ID, session token, or query parameters.

## Bundle size and CPU

`bun run deploy:check` (the e2e test Worker, `wrangler deploy --dry-run`):

| Build                                    | Total upload | gzip       |
| ---------------------------------------- | ------------ | ---------- |
| Before (raw D1)                          | 3,251.25 KiB | 671.66 KiB |
| Drizzle, `betterAuth` from `better-auth` | 3,470.48 KiB | 713.11 KiB |
| Drizzle, `better-auth/minimal` (chosen)  | 2,748.95 KiB | 610.66 KiB |

`drizzle-orm` adds about 172 KiB before compression. `better-auth/minimal`
removes Kysely (about 607 KiB) and the Kysely adapter (about 54 KiB).

CPU was measured roughly in Bun, not in workerd: the HTTP test harness with
the `bun:sqlite` D1 stand-in, 1,000 requests after 50 warm-up requests,
`process.cpuUsage()` per request, main and this branch run one after the
other on the same machine, two runs each:

| Request                                  | Before       | Drizzle      |
| ---------------------------------------- | ------------ | ------------ |
| Contact POST (insert + prune claim)      | 0.23 ms      | 0.49–0.50 ms |
| Admin list, page 1 (session and queries) | 0.81–0.83 ms | 1.26–1.27 ms |
| Admin list, `status=new&page=2`          | 0.66 ms      | 1.06–1.09 ms |
| Building `betterAuth()` (first use)      | 0.31–0.35 ms | 0.40–0.47 ms |

Per query, Drizzle adds about 50–80 µs of query building in Bun. That is
small next to the free plan's 10 ms CPU limit, but it is not zero. Real CPU
time on Workers was not measured; check it in Workers observability after
the first deploy. Drizzle's prepared queries would remove most of the query
building, if it ever matters.

## Consequences

- App code has no SQL strings except a few `sql` template fragments
  (`coalesce(read_at, ?)`, the `excluded.value` upsert, a cast) whose values
  are bound.
- Tests check that input is bound: `submission-store.test.ts` records every
  statement sent to the D1 stand-in and checks that an injection string
  appears only in the parameters and that the SQL text is the same for every
  status, limit, and offset (a zero offset leaves out the `offset ?` clause).
  The route tests send `new' OR 1=1 --`, `1; DROP TABLE submissions`, `-1`,
  `1e9`, `50 OFFSET 0`, fractions, hex, and empty values and expect 400.
- Better Auth columns changed from camelCase (`userId`) to snake_case
  (`user_id`), and timestamps from text to integer milliseconds. Test helpers
  and the e2e queries were updated.
- Better Auth upgrades: regenerate the Better Auth part of `schema.ts` with
  the CLI, then `bun run db:generate`.
- The trigger is invisible to drizzle-kit; the rules above keep it in place.
