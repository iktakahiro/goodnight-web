Right after a deploy, the site has no admin. This page shows how you create the first one, and how goodnight-web stops a stranger from getting there first.

## The setup screen

Opening `/admin/` on a site without an admin shows the setup screen at `/admin/setup`.

/>

Setup has three steps:

1. **Check the setup token.** Enter the value of `SETUP_TOKEN`, an address from `ADMIN_EMAILS`, and optionally your name, then select **Continue**. If the check passes, you are signed in and move on to step 2. A wrong token, an address that is not allowed, and a closed setup each get their own message.
2. **Register a passkey.** Select **Register a passkey**. Your browser, phone, or password manager creates the passkey and asks for your fingerprint, face, or PIN. The screen shows the domain the passkey belongs to.
3. **Done.** Setup is closed and you are signed in. Select **Open inquiries** to go to the admin screen. Next time, sign in at `/admin/login` with the passkey.

When you are done, delete the `SETUP_TOKEN` secret. It is not needed again.

If you leave after step 1, opening `/admin/setup` again continues at step 2. Leaving before you register a passkey does not lock you out.

## What setup accepts

The setup endpoint `/api/setup` creates the first admin. It accepts a request only if:

- the request comes from the site itself (the `Origin` header is checked),
- the request uses `https://` (plain HTTP is allowed only on `localhost`),
- the request includes the correct `SETUP_TOKEN` (compared in constant time, so the response time does not give the token away), and
- the email address is in `ADMIN_EMAILS` (case-insensitive).

Setup is also off in these cases:

- **The rate limit cannot run.** Setup attempts are rate-limited. Without the Rate Limiting binding or `IP_HASH_SECRET`, setup is turned off.
- **A setting is missing or a secret is too short.** `SETUP_TOKEN`, `BETTER_AUTH_SECRET`, and `IP_HASH_SECRET` must be at least 32 characters. When a required setting is missing or too short, the setup screen shows its name.

## How setup closes

Once the first passkey is registered, setup is closed and the setup endpoint stops working. It stays closed even if every passkey is deleted later.

Setup counts as closed when `settings.setup_closed_at` exists or any passkey exists. The first passkey registration writes `setup_closed_at` itself (see [Sessions](#sessions)).

A database trigger also writes `setup_closed_at` whenever a row is inserted into `passkey`, so `setup_closed_at` stays even if every passkey is deleted:

```sql title="packages/server/migrations/0002_setup_closed_trigger.sql"
CREATE TRIGGER `passkey_closes_setup` AFTER INSERT ON `passkey`
BEGIN
  INSERT OR IGNORE INTO `settings` (`key`, `value`)
    VALUES ('setup_closed_at', CAST(strftime('%s', 'now') AS INTEGER) * 1000);
END;
```

The admin API accepts only a signed-in user who is still in `ADMIN_EMAILS` and has a passkey. The session created during setup can only be used to register the first passkey.

## Sessions [#sessions]

Someone else who had the token earlier could have run setup with the same address and kept the session. These rules make sure such a session never becomes an admin session:

- **Running setup again clears old sessions.** When setup runs again for an address that already has a user, that user's earlier sessions are deleted.
- **Only one passkey registration can claim setup.** Before the passkey is saved, the registration claims setup: one SQL statement writes `setup_closed_at` only if it is not there yet. If two people try to register the first passkey at the same time, only one claim succeeds. The other registration gets 403.
- **The claim deletes every session.** At this point, the only sessions are the ones setup created. The setup screen registers the passkey with `createSession`, so you get a new session, created after the passkey, and stay signed in.
- **A failed save undoes the claim.** If the passkey cannot be saved after the claim, the claim is removed, so you can run setup again. The removal matches only that claim, and only while no passkey exists.
- **Setup checks again at the end.** After setup creates its session, it checks that setup is still open. If a passkey registration claimed setup in the meantime, setup deletes that session and returns 403.
- **No passkey registration after setup closes.** Once setup is closed, a user without a passkey cannot register one.
- **Old sessions do not work.** The admin API rejects (401) a session created before the user's first passkey. A user who already has a passkey can register another one through the passkey API only from a session created at or after the first passkey, so an old setup session cannot add one. The admin screen has no page to add a passkey yet.

Just before the first passkey is saved, the passkey registration hook stops if setup is closed, claims setup, and deletes every session:

```ts title="packages/server/src/features/setup/first-passkey.ts"
if (await isSetupClosed(db)) {
  throw new APIError('FORBIDDEN', { message: 'setup closed' });
}
const claim = await claimSetup(db);
if (!claim) throw new APIError('FORBIDDEN', { message: 'setup closed' });
claims.set(request, claim);
await getDatabase(db).delete(sessionTable);
```

The claim is one `INSERT ... ON CONFLICT DO NOTHING` statement. Only the registration that writes the row goes on:

```ts title="packages/server/src/features/setup/setup-state.ts"
export const claimSetup = async (db: D1Database): Promise<string | null> => {
  const value = String(Date.now());
  const rows = await getDatabase(db)
    .insert(settings)
    .values({ key: SETUP_CLOSED_AT, value })
    .onConflictDoNothing()
    .returning({ value: settings.value });
  return rows.length === 1 ? value : null;
};
```

The admin API compares the session's creation time with the user's first passkey:

```ts title="packages/server/src/features/auth/passkey-session.ts"
const first = await getDatabase(db)
  .select({ createdAt: passkey.createdAt })
  .from(passkey)
  .where(and(eq(passkey.userId, userId), isNotNull(passkey.createdAt)))
  .orderBy(asc(passkey.createdAt))
  .get();
if (!first?.createdAt) return 'no_passkey';
return sessionCreatedAt.getTime() < first.createdAt.getTime()
  ? 'too_old'
  : 'ok';
```

## Why it is built this way

A newly deployed site is public on the internet before its owner has signed in. If the first visitor to the setup page became the admin, a stranger who found the site first could take it over.

So setup requires both a secret that only the owner knows and an allowed address. Setup closes afterwards, so a leaked `SETUP_TOKEN` cannot create more admins later.

If Cloudflare Access protects `/admin`, `/admin/*`, `/api/admin/*`, `/api/setup`, and `/api/auth/*`, only people who pass Access can reach setup at all. With `ACCESS_AUD` and `ACCESS_TEAM_DOMAIN` set, the Worker also checks the Access token on `/api/setup` itself. See [Security model](/docs/security/#cloudflare-access).
