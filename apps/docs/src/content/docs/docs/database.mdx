## Tables

Each site has one D1 database. `@goodnight-web/server` defines every table in one schema file, `packages/server/src/db/schema.ts`, written with [Drizzle ORM](https://orm.drizzle.team/).

| Table                                                   | Contents                                                                                                                                        |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `submissions`                                           | Contact form submissions: name, address, message, category, status, spam score, `ip_hash` (an HMAC of the IP address, never the address itself) |
| `settings`                                              | `retention_days`, `last_cleanup_at` (for [data pruning](/docs/how-it-works/data-pruning/)), and `setup_closed_at`                               |
| `user`, `session`, `account`, `verification`, `passkey` | Better Auth: admins, sessions, and passkeys                                                                                                     |

Times are stored as Unix milliseconds. The Better Auth tables are generated by the Better Auth CLI for its Drizzle adapter, so Better Auth and the rest of the server use the same schema and the same migration history.

## How queries are written

The server never builds SQL text from input. Every query goes through the Drizzle query builder, which sends values to D1 as bound parameters. See [SQL injection](/docs/security/#sql-injection) on the security page.

## How migrations ship and run

The package contains the SQL migrations generated by drizzle-kit:

```txt
node_modules/@goodnight-web/server/migrations/
  0000_initial_schema.sql
  0001_settings_defaults.sql
  0002_setup_closed_trigger.sql
```

Your site's `wrangler.jsonc` points the D1 binding at that directory:

```jsonc
"d1_databases": [
  {
    "binding": "DB",
    "migrations_dir": "node_modules/@goodnight-web/server/migrations"
  }
]
```

The deploy script applies them before the new code goes live:

```sh
wrangler d1 migrations apply DB --remote && wrangler deploy
```

Wrangler sorts the files by name and records each applied file in a `d1_migrations` table in your database. A file that is already recorded is skipped, so running the command again does nothing. If a file fails, D1 rolls it back and the deploy stops before `wrangler deploy`.

You do not write migrations for your site. Do not run `wrangler d1 migrations create`: it would write a file into `node_modules`.

## How a schema change reaches your site

1. goodnight-web changes the schema, generates a new migration file such as `0003_add_note.sql`, and publishes a new version of `@goodnight-web/server`. Released migration files are never edited or renamed.
2. Dependabot opens a pull request that updates `@goodnight-web/server` in your repository. See [Distribution and updates](/docs/distribution/).
3. You merge it. The deploy script applies `0003_add_note.sql` and then deploys the new code.

Between the two commands, the old version of the Worker runs against the new schema. goodnight-web keeps schema changes additive (new tables and columns), and the queries name their columns, so the old version keeps working during that time.

Preview builds of a pull request do not run the deploy script, so they use your database without the new migration. A screen that needs the new schema can fail in the preview. This is not verified yet.

## Undoing a migration with Time Travel

D1 Time Travel can restore the whole database to an earlier minute: up to 7 days back on the Workers free plan and up to 30 days on the paid plan ([Cloudflare: Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)).

```sh
wrangler d1 time-travel info DB --timestamp=2026-10-22T09:00:00Z
wrangler d1 time-travel restore DB --timestamp=2026-10-22T09:00:00Z
```

A restore also removes every inquiry and every sign-in that happened after that time, and it does not change the deployed code. If you restore to a time before a migration, deploy the matching older version of your site too. Otherwise the deploy script applies the migration again on the next deploy.
