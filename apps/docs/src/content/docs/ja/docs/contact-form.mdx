## フォームを編集する

管理画面にログインし、**フォーム**（英語表示では Form）を開きます。**お問い合わせフォーム**という見出しのページに項目が順番に並んでいて、次のことができます。

- 項目の追加、削除、上下の並べ替え
- 種類、ラベル、任意のプレースホルダーと補足説明（それぞれ日本語と英語）、必須かどうか、テキスト項目の最大文字数の設定
- セレクト、ラジオボタン、チェックボックスの選択肢の追加、削除、並べ替え
- 問い合わせ一覧に列として出すかどうか（**一覧に表示**）の設定
- 日本語と英語でのフォームのプレビュー

**保存**すると、項目が新しいバージョンとして保存されます。問い合わせページは、訪問者が開いたときに現在のバージョンを読み込むので、変更は 30 秒ほど（フォームがキャッシュされうる時間）で訪問者に届きます。`site.config.ts` の編集もデプロイもいりません。

最初のバージョンは、スターターに付いているフォームと同じです。お名前（必須）、会社名、電話番号、お問い合わせの種類（選択肢 5 つのセレクト）、お問い合わせ内容（必須）です。

## 変えられない部分

次の部分はいつもフォームにあり、編集できません。

| 部分                         | 固定している理由                                                                                                                  |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| メールアドレス（必須）       | 返信先であり、すべての問い合わせが持つ唯一の列です。フォームの中身がどうであっても、一覧、詳細、CSV、返信ボタンはこれを使います。 |
| プライバシーポリシーへの同意 | 同意のない送信は API が受け付けません。同意した時刻を保存します。                                                                 |
| honeypot の欄                | ボットだけが入力する、見えない欄です。[問い合わせフォームの保護](/ja/docs/how-it-works/contact-protection/)を参照してください。   |
| Turnstile                    | 保存の前にサーバーが確認する、ボット対策です。                                                                                    |

編集画面では、メールアドレスの行は固定として表示し、この理由を添えています。

## 項目の種類と上限

| 種類       | 保存する値                     | 補足                                                     |
| ---------- | ------------------------------ | -------------------------------------------------------- |
| `text`     | 1 行のテキスト                 | 制御文字を除き、前後の空白を取ります                     |
| `textarea` | 改行を含むテキスト             |                                                          |
| `tel`      | テキスト                       | 数字、`+`、`-`、`(`、`)`、空白。全角の数字も受け付けます |
| `url`      | テキスト                       | `http://` か `https://` だけ                             |
| `number`   | 数値                           |                                                          |
| `date`     | `YYYY-MM-DD`                   | 実在する日付であること                                   |
| `select`   | 選択肢の値 1 つ                | その項目の選択肢のどれかであること                       |
| `radio`    | 選択肢の値 1 つ                | その項目の選択肢のどれかであること                       |
| `checkbox` | 選択肢の値のリスト（1 つ以上） | それぞれがその項目の選択肢のどれかであること             |

| 上限                                                 | 値             |
| ---------------------------------------------------- | -------------- |
| 1 バージョンの項目数（メールアドレスと同意を除く）   | 30             |
| 1 項目の選択肢の数                                   | 50             |
| ラベル（項目と選択肢）、言語ごと                     | 100 文字       |
| プレースホルダー、言語ごと                           | 100 文字       |
| 補足説明、言語ごと                                   | 200 文字       |
| `text`、`tel`、`url` の最大文字数                    | 1〜2,000 文字  |
| `textarea` の最大文字数                              | 1〜10,000 文字 |
| 問い合わせ 1 件の保存する値（JSON、UTF-8）           | 16 KB          |
| `POST /api/contact` のリクエスト本文（読む前に確認） | 32 KB          |

ラベルは、少なくとも一方の言語で入力が必要です。片方の言語が空のときは、もう一方を表示します。

## 項目の ID

項目にはそれぞれ `f_k3v9q2m8x1b7c4d6` のような ID があります。項目を最初に保存したときにサーバーが作り、その後は変わりません。編集画面で見たり入力したりすることはありません。値はラベルではなく、この ID で保存します。

```ts title="packages/server/src/features/contact-form/form-definition.ts"
export const FIELD_ID_PATTERN = /^f_[a-z0-9]{1,32}$/;
```

バージョンごとに、次の形の定義を保存します（ラベル、プレースホルダー、補足説明は `ja` と `en` の文を持ちます）。

```ts title="packages/server/src/features/contact-form/form-definition.ts"
/** A field of the contact form. */
export interface FormField {
  /** Immutable id, generated by the server. Matches {@link FIELD_ID_PATTERN}. */
  id: string;
  type: FormFieldType;
  label: LocalizedText;
  placeholder?: LocalizedText;
  /** Help text shown under the field. */
  hint?: LocalizedText;
  required: boolean;
  /** Text types only. Defaults to {@link DEFAULT_MAX_LENGTH}. */
  maxLength?: number;
  /** Choice types only: 1 to {@link FORM_LIMITS}.options entries. */
  options?: FormFieldOption[];
  /** Shown as a column in the admin list by default. */
  showInList: boolean;
}
```

```ts title="packages/server/src/features/contact-form/form-definition.ts"
/** The stored definition of one version. */
export interface FormDefinition {
  /** The fields on the form, in order. */
  fields: FormField[];
  /** Fields removed in this or an earlier version, newest removal first. */
  archived: ArchivedFormField[];
}
```

このため、次のようになります。

- **ラベルを変えてもデータはそのまま。** 「会社名」を「団体名」に変えても ID は同じなので、変更の前と後の回答は同じ列に入ります。
- **新しい項目が古い項目の代わりになることはありません。** 「ご予算」を削除し、後で同じ「ご予算」という項目を追加すると、新しい項目には新しい ID が付きます。ラベルが同じでも、古い回答と新しい回答は分かれたままです。
- **ID はブラウザからは選べません。** 編集画面は新しい項目を ID なしで送ります。フォームのどのバージョンにもなかった ID は、400 で拒否します。
- **種類は、値の形が同じものの間でだけ変えられます。** `text`、`textarea`、`tel`、`url` は互いに変えられます。`select` と `radio` も同じです。それ以外の変更（たとえば `text` から `number`）は拒否します。その ID で保存済みの値が、新しい種類に合わなくなるからです。その場合は新しい項目を追加してください。
- **選択肢の値も自動で作ります。** 新しい選択肢には `o_p4n8w2k6c1` のような値が付きます。編集するのはラベルです。

## バージョンと履歴

保存するたびにバージョンが 1、2、3 と増えます。ラベル、種類、選択肢、順番、設定のどれを変えても、新しいバージョンになります。何も変えずに保存したときは増えません。

- バージョンは追記だけです。データベースのトリガーが `form_definitions` テーブルへの `UPDATE` と `DELETE` を拒否するので、保存したバージョンが変わることはありません。
- **フォーム**のページには、バージョン番号、日時、保存した管理者の履歴が並びます。
- **復元**は、古いバージョンの項目を新しいバージョンとして保存します。履歴を巻き戻したり、何かを消したりはしません。復元した項目は ID がそのままなので、データもまたつながります。
- 編集中にほかの人が保存していたら、保存は拒否されます（409 `form_conflict`）。再読み込みして、もう一度変更してください。

## 項目の削除と、元に戻すこと

項目を削除すると、アーカイブされます。何も消えません。

- その項目は古いバージョンに残り、保存済みの回答も問い合わせに残ります。
- 定義には、アーカイブした項目の一覧が、最後のラベルと、最後にその項目があったバージョンと一緒に残ります。
- 編集画面にはアーカイブした項目が並びます。元に戻すと、前と同じ ID のままフォームに戻ります。

## 問い合わせ一覧

### 状態: 未読と既読

問い合わせの状態は**未読**と**既読**の 2 つだけです。新しい問い合わせは未読です。詳細を開くと既読になります。あとで対応するために、一覧（状態の横の封筒のボタン）か詳細から未読に戻せます。ほかの状態はありません。対応の記録が必要なら、メールで返信するか、CSV に書き出してください。

**スパムの疑い**は状態ではありません。honeypot かスパムスコア（[問い合わせフォームの保護](/ja/docs/how-it-works/contact-protection/)を参照）か管理者が付ける、別の印です。スパムの疑いがある問い合わせにも、未読と既読があります。

ヘッダーの未読件数は、スパムの疑いがない未読の問い合わせの数です。

### 列

一覧には、受信日時、メールアドレス、状態（当てはまればスパムの疑いの印も）の 3 つの固定の列があります。その後に、現在のバージョンの項目が続きます。**一覧に表示**がオンの項目は、最初から表示されます（最初のバージョンでは、お名前、会社名、お問い合わせ内容。長い文は 120 文字で切ります）。列ごとに表示と非表示を切り替えられ、その選択はそのブラウザにだけ保存されます（`localStorage`）。アーカイブした項目は一覧には出ません。

### 表示の切り替えと絞り込み

上部のタブで、表示する問い合わせを選びます。

| タブ                     | 表示する問い合わせ                       |
| ------------------------ | ---------------------------------------- |
| 未読                     | スパムの疑いがない未読の問い合わせ       |
| 既読                     | スパムの疑いがない既読の問い合わせ       |
| すべて（最初に開くタブ） | スパムの疑いがないすべての問い合わせ     |
| スパムの疑い             | スパムの疑いがあるものだけ（未読と既読） |

「未読」と「スパムの疑い」のタブには件数を表示します。「未読」「既読」「すべて」のタブでは、スパムの疑いがある問い合わせは「スパムの疑い」のタブにあることを、そのタブへのリンクと一緒に示します。

スパムの疑いを別のタブに分けるのは、混ぜると本物の問い合わせがスパムに埋もれ、未読件数も役に立たなくなるからです。消えるわけではありません。保存され、件数も出ていて、1 回の操作で見られます。

それぞれのタブの中で、さらに次の絞り込みができます。

- フォームのバージョン
- 現在のバージョンにあるセレクトかラジオボタンの選択肢

### 並び順

並び順は受信日時だけです。最初は新しい順で、**受信日時**の列見出しを選ぶと古い順になります。メールアドレス、状態、フォームの項目では並べ替えられません。管理者が問い合わせを探す手がかりは受信日時だからです。

### メールアドレスで検索

検索欄に入力した文字を含むメールアドレスの問い合わせを探します。大文字と小文字は区別しません。`example.co` で `taro@example.com` も `info@example.co.jp` も見つかります。検索するのは固定のメールアドレスの列だけで、フォームの項目は検索しません。

検索する文字は 254 文字（メールアドレスの最大の長さ）までです。検索は、選んでいるタブと絞り込みの中で行い、CSV の書き出しも同じ条件になります。

フォームの項目の値で問い合わせを探すときは、選択肢での絞り込みか CSV の書き出しを使ってください。

## 問い合わせの詳細

詳細では、それぞれの問い合わせを、送信されたときのバージョンのラベルと順番で表示します。現在のフォームにない項目の値も表示し、バージョン N のもので、アーカイブ済みであることを示します。後でラベルを変えても、古い問い合わせの見え方は変わりません。

## CSV の書き出し

CSV には、固定の列（`id`、`received_at`、`status`（`unread` か `read`）、`suspected_spam`（`1` か `0`）、`email`、`locale`、`form_version`、`page_path`、`country`、`spam_score`、`spam_reasons`）の後に、フォームにこれまであったすべての項目 ID の列が続きます。順番は、現在の項目（フォームの順）、アーカイブした項目です。

- 見出しは、選んだ言語（日本語か英語）のラベルです。
- アーカイブした項目の見出しには、最後にその項目があったバージョンを付けます。たとえば `ご予算 (v3)` です。同じラベルの新しい項目は、別の列 `ご予算` になります。
- それでも見出しが重なるときは、項目 ID を角かっこで付けます。
- セレクト、ラジオボタン、チェックボックスの値は、選択肢のラベルで書き出します。
- 表計算ソフトの数式のように始まるセル（`=`、`+`、`-`、`@`、タブ）には、先頭に `'` を付けます。
- 書き出しは、一覧の表示、メールアドレスの検索、絞り込みに従います。「すべて」にはスパムの疑いが入らないので、必要なら「スパムの疑い」の表示で書き出してください。
- ファイルは 200 行ずつ読んで順に送り出すので、大きなテーブルでも全体をメモリに載せません。
- 書き出しに含まれるのは、書き出しを始めたときに現在だったフォームのバージョンと、それより前のバージョンで送られた問い合わせです。書き出しの途中で新しいバージョンが保存されたときは、そのバージョンで送られた問い合わせは含めません。見出しに、そのバージョンで増えた項目の列がないからです。次の書き出しには含まれます。

## なぜこう作るか

- **定義は D1 にあるので、コードを書かない人でも変えられます。** 小さな会社では、エンジニアがすぐそばにいないことがよくあります。「ご予算」の欄を足すのに、コードの変更、ビルド、デプロイが必要であるべきではありません。
- **サーバーは D1 にある定義だけを信じます。** `GET /api/contact/form` の定義は、フォームを表示するためのものです。送信のときは、サーバーが D1 から定義を読み直し、それで確かめます。書き換えたページや手で作ったリクエストで、項目を増やしたり確認を飛ばしたりはできません。
- **項目ごとの列ではなく、1 つの JSON の列。** 項目ごとに列を作ると、フォームを変えるたびにスキーマのマイグレーションが必要になり、マイグレーションはパッケージのリリースでしか届きません。項目 ID をキーにした JSON の列なら、マイグレーションはいりません。
- **変わらない ID とバージョンで、データを混ぜません。** ラベルは変わり、項目は増えたり減ったりします。値は使い回されない ID で保存し、問い合わせごとにバージョンを記録するので、別の質問への回答が同じ列に入ることはなく、どの問い合わせも訪問者が見たフォームのとおりに表示できます。
- **メールアドレスは固定です。** どの問い合わせにも返信の手段が必要です。普通の列として持つので、フォームの中身に関係なく、一覧で検索でき、詳細には返信ボタンを出せます。
- **Slack に個人情報は送りません。** フォームにどんな項目があっても、通知は「新しい問い合わせ 1 件」、受信日時、リンクだけです。[Slack 通知](/ja/docs/how-it-works/notifications/)を参照してください。

## 開発者向けの詳細

ここから下は、サーバーのコードを読む人や変える人に向けた説明です。管理画面を使うだけなら、読まなくてかまいません。

### 一覧の絞り込みと検索のしくみ

選択肢での絞り込みは、保存した JSON に `json_extract()` を使います。項目の ID はまず保存済みの定義から探し、JSON のパスと値はどちらもバインドされたパラメーターとして渡します。

```ts title="packages/server/src/features/submissions/submission-store.ts"
choiceIs = sql`json_extract(${submissions.fields}, ${`$.${choice.fieldId}`}) = ${choice.value}`;
```

並び順を受信日時だけにしている理由は、管理者の探し方のほかにもあります。フォームの項目の値は 1 つの JSON の列に入っているので、項目で並べ替えると、項目ごとに別のクエリプランになってしまいます。

メールアドレスの検索は、`lower(email)` に Drizzle の `like` を使い、値を 1 つのバインドされたパラメーターで渡します。検索する文字の中の `%`、`_`、`\` はエスケープするので、ただの文字として一致します。

```ts title="packages/server/src/features/submissions/submission-store.ts"
export const escapeLike = (term: string): string =>
  term.replace(/[\\%_]/g, (char) => `\\${char}`);

/**
 * Case-insensitive partial match on `email`. The pattern is one bound
 * parameter; only the `ESCAPE` character is part of the SQL text.
 */
const emailContains = (term: string): SQL =>
  sql`${like(
    sql`lower(${submissions.email})`,
    `%${escapeLike(term.toLowerCase())}%`,
  )} escape '\\'`;
```

**この検索用のインデックスを作らない理由。** `LIKE '%文字%'` の検索はインデックスを使えないので、D1 は `submissions` のすべての行を読みます。問い合わせフォームなら、これで問題ありません。問い合わせの多い小さな会社でも件数は年に数千件で、保持期間（既定は 180 日）を過ぎた行は削除されます。短い行を数千件読むのは数ミリ秒で、D1 の読み取り行数もわずかです。インデックスを増やすと INSERT のたびに遅くなるうえ、部分一致には役に立ちません。並び順と保持期間による削除には `created_at` のインデックスを使います。

**フォームの項目を検索しない理由。** 自由に書かれた文を検索するには、保存したすべての値への `LIKE` か、フォームの変更のたびに追従する全文検索のインデックスが必要になります。よくある用途は、絞り込みと CSV の書き出しで足ります。

### 問い合わせページがフォームを取得する流れ

ページは、公開されている読み取り専用のエンドポイントから現在のフォームを読みます。

```http
GET /api/contact/form
```

応答には、バージョン、項目（ID、種類、ラベル、プレースホルダー、補足説明、必須、最大文字数、選択肢）、固定のメールアドレス欄、フォームが使えるかどうか（Turnstile のサイトキー、action、honeypot の名前）が入っています。シークレットは含みません。30 秒までキャッシュされることがあります（`Cache-Control: public, max-age=30`）。

スターターは、読み込み中の表示を出しながら、ブラウザでフォームの項目を表示します。取得に失敗したときは、`site.config.ts` の会社のメールアドレスを添えた短いメッセージを出します。ブラウザ用のヘルパーは、`@goodnight-web/server/client` の `getContactForm()` です。

ページは、表示したフォームのバージョンを `formVersion` として送ります。その間にフォームが変わっていたら、API は 409 `form_outdated` を返します。スターターはフォームを読み込み直し、残っている項目に入力済みの内容を残したまま、もう一度送信するよう案内します。

### サーバーが送信内容を確かめる流れ

サーバーは、D1 にある現在のバージョンから zod のスキーマを組み立て、`fields` を確かめます。ブラウザから送られた定義は使いません。組み立てたスキーマは、Worker の isolate ごと、バージョンごとにキャッシュします。リクエストごとに読むのは、現在のバージョン番号だけです。

- 受け付けるのは、現在の項目の ID だけです。それ以外のキーは、`__proto__` も含めて 400 で拒否します。
- 必須、文字数、形式、選択肢の値を確かめます。テキストは固定の項目と同じように整えます。
- 空の任意項目は、保存する JSON に入れません。

ルートは現在のバージョンを読み、古いページからの送信を断り、そのバージョンのスキーマで値を確かめます。

```ts title="packages/server/src/features/contact/contact-routes.ts"
const data = parsed.data;
const form = await getCurrentForm(env.DB);
if (data.formVersion !== undefined && data.formVersion !== form.version) {
  return apiError(c, 409, 'form_outdated');
}
const fields = form.definition.fields;
const values = valuesSchemaFor(env.DB, form.version, fields).safeParse(
  data.fields,
);
if (!values.success) {
  return apiError(
    c,
    400,
    'invalid_input',
    contactFieldErrors(values.error, input, 'fields'),
  );
}
```

スキーマはまずキーを確かめます。パースした JSON そのものに対して、何かをコピーする前に行います。

```ts title="packages/server/src/features/contact-form/form-values-schema.ts"
const shape: Record<string, z.ZodType> = {};
for (const field of fields) shape[field.id] = valueSchema(field);
const ids = new Set(fields.map((field) => field.id));
// Checked by own keys first, on the parsed JSON itself: JSON.parse()
// creates `__proto__` as an own key, which copying into a new object or a
// key lookup with `in` would silently drop or accept.
return z
  .custom<Record<string, unknown>>(
    (value) =>
      typeof value === 'object' && value !== null && !Array.isArray(value),
  )
  .superRefine((values, ctx) => {
    const unknown = Object.keys(values).filter((key) => !ids.has(key));
    if (unknown.length > 0) {
      ctx.addIssue({
        code: 'unrecognized_keys',
        keys: unknown,
        input: values,
      });
    }
  })
  .pipe(z.strictObject(shape))
```

問い合わせは、値を項目 ID をキーにした JSON として `submissions.fields` に、バージョンを `submissions.form_version` に保存します。[データベースとマイグレーション](/ja/docs/database/)を参照してください。
