管理者は、`/admin/login` で Better Auth のパスキーを使ってログインします。メールとパスワードでのログインはありません。このページでは、そのしくみと理由を説明します。

## 使う前に知っておくこと

- **パスキーは 1 つのドメインに結びつきます。** パスキーは独自ドメインを追加してから登録してください。`workers.dev` のアドレスで登録したパスキーは、独自ドメインでは使えません。
- **同期されるパスキーを使ってください。** 管理画面には、2 つ目のパスキーを追加する画面がまだありません。セットアップでブラウザが保存先を聞いてきたら、端末の間で同期される保存先（iCloud キーチェーン、Google パスワードマネージャー、パスワード管理アプリなど）を選んでください。1 台の端末をなくしても、ほかの端末からログインできます。
- **パスキーをすべてなくすと、ログインできなくなります。** 管理者を取り戻す手順は、まだありません。セットアップも開き直せません（[最初の管理者の作成](/ja/docs/how-it-works/first-admin/)を参照）。
- **2 人目の管理者は追加できません。** セットアップが完了したあとは、パスキーを持たないユーザーは新しくパスキーを登録できないからです。

## 何をするか

- **Better Auth とパスキープラグインを使います。** 管理画面と管理 API は [Better Auth](https://better-auth.com/) とそのパスキープラグインを使います。ユーザー、セッション、パスキーは、同じ D1 データベースに保存します。
- **ほかの入り口はありません。** メールとパスワードでのログインは無効です。開発用の抜け道、既定のアカウント、共有のキーもありません。
- **本人確認が必要です。** パスキーの登録とログインには、PIN や生体認証による本人確認が必要です。
- **IP アドレスを記録しません。** Better Auth はセッションに IP アドレスを記録しません。
- **ログインには回数制限があります。** 問い合わせフォームと同じ Rate Limiting binding で、ハッシュ化した IP アドレスごとに数えます。その binding か `IP_HASH_SECRET` がなければ、ログインは使えません。
- **`https://` でだけ動きます。** ログイン、セットアップ、管理画面、管理 API が対象です。`wrangler dev` のために、`localhost` では平文の HTTP も使えます。[セキュリティモデル](/ja/docs/security/#https)を参照してください。
- **Cloudflare Access を前に置けます。** `/admin`、`/admin/*`、`/api/admin/*`、`/api/setup`、`/api/auth/*` が対象です。`ACCESS_AUD` と `ACCESS_TEAM_DOMAIN` を設定すれば、Worker も Access のトークンを確認します。Access を使っても、パスキーでのログインは必要です。[セキュリティモデル](/ja/docs/security/#cloudflare-access)を参照してください。
- **パスキーより前のセッションは使えません。** 管理 API は、最初のパスキーより前に作られたセッションを受け付けません。受け付けるのは、パスキーでのログインか、最初のパスキーの登録で作られたセッションです。[最初の管理者の作成](/ja/docs/how-it-works/first-admin/#sessions)を参照してください。
- **インスタンスを使い回します。** Better Auth のインスタンスは、必要になったときに Worker の binding から作り、同じ isolate の後のリクエストでも使い回します。作るのに CPU を約 5 ms 使うので、毎回作ると無料プランの上限の半分を使ってしまいます。binding が変われば、新しいインスタンスを作ります。

## コードでは

Better Auth は `emailAndPassword: { enabled: false }` で設定し、IP アドレスの記録も切っています（`advanced.ipAddress.disableIpTracking`）。

パスキープラグインには、リクエストのホスト名を relying party ID として渡し、本人確認を必須と指定します。ただしプラグインは、登録の検証で本人確認を強制しません。そのため、登録のフックで確かめます。

```ts title="packages/server/src/features/auth/auth.ts"
passkey({
  rpID: new URL(origin).hostname,
  rpName: 'goodnight-web',
  origin,
  authenticatorSelection: {
    residentKey: 'required',
    userVerification: 'required',
  },
  // The plugin verifies with requireUserVerification: false, so enforce
  // user verification (PIN or biometrics) here.
  registration: {
    afterVerification: async ({ ctx, verification, user }) => {
      if (!verification.registrationInfo?.userVerified) {
        throw new APIError('UNAUTHORIZED', {
          message: 'user verification required',
        });
      }
```

インスタンスは isolate ごとにキャッシュし、`env` オブジェクトとオリジンをキーにします。

```ts title="packages/server/src/features/auth/auth.ts"
// Building betterAuth() costs about 5 ms of CPU, close to the free plan's
// 10 ms limit, so instances are reused within an isolate. They are keyed by
// the env object (a new env means new bindings or secrets) and by origin
// (passkeys are bound to the hostname). See docs/decisions/0001.
const cache = new WeakMap<GoodnightEnv, Map<string, GoodnightAuth>>();
```

```ts title="packages/server/src/features/auth/auth.ts"
export const getAuth = (env: GoodnightEnv, origin: string): GoodnightAuth => {
  let byOrigin = cache.get(env);
  if (!byOrigin) {
    byOrigin = new Map();
    cache.set(env, byOrigin);
  }
  let auth = byOrigin.get(origin);
  if (!auth) {
    auth = buildAuth(env, origin);
    byOrigin.set(origin, auth);
  }
  return auth;
};
```

## なぜパスキーか

- **盗まれたり使い回されたりするパスワードがありません。** パスキーはドメインに結びつくので、別のドメインのフィッシングサイトでは使えません。
- **無料プランの CPU の上限に収まります。** 無料プランの Worker が 1 回のリクエストで使える CPU 時間は 10 ms ほどです。パスワードのハッシュ（scrypt）はわざと遅く作られていて、Workers 上で Better Auth のパスワード処理がこの上限を超えるという報告があります（[better-auth#8860](https://github.com/better-auth/better-auth/issues/8860)）。パスキーのログインは署名を確かめるだけなので速く済みます。
- **ほかに動かすものがいりません。** パスキーには、メール送信のサービスも SMS のサービスも必要ありません。
