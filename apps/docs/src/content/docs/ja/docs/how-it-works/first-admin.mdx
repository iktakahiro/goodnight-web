## 何をするか

デプロイした直後のサイトには、管理者がいません。セットアップ用のエンドポイント `/api/setup` が最初の管理者を作ります。受け付けるのは、次のすべてを満たすリクエストだけです。

- サイト自身から送られている（`Origin` ヘッダーを確認します）。
- `https://` で送られている（平文の HTTP は `localhost` でだけ使えます）。
- 正しい `SETUP_TOKEN` が含まれている（比較にかかる時間が一定になる方法で比べます）。
- メールアドレスが `ADMIN_EMAILS` に入っている（大文字と小文字は区別しません）。

セットアップの試行回数にも制限があります。この制限をかけられないとき（Rate Limiting binding か `IP_HASH_SECRET` がないとき）は、セットアップは使えません。`SETUP_TOKEN`、`BETTER_AUTH_SECRET`、`IP_HASH_SECRET` は 32 文字以上が必要です。短い値があるとセットアップは使えず、セットアップ画面にその設定の名前を表示します。新しい管理者はログインした状態になり、続けてパスキーを登録します。最初のパスキーが登録されるとセットアップは完了し、セットアップのエンドポイントは使えなくなります。後でパスキーをすべて削除しても、完了した状態が続きます。それまではセットアップをやり直せるので、パスキーを登録する前に離れても締め出されません。

`settings.setup_closed_at` があるか、パスキーが 1 つでもあれば、セットアップは完了しているとみなします。`setup_closed_at` は、最初のパスキーを登録する処理が書き込みます（[セッション](#sessions)を参照）。さらに、パスキーの行が追加されるたびにデータベースのトリガーも書き込むので、後でパスキーをすべて削除しても印は残ります。

```sql title="packages/server/migrations/0002_setup_closed_trigger.sql"
CREATE TRIGGER `passkey_closes_setup` AFTER INSERT ON `passkey`
BEGIN
  INSERT OR IGNORE INTO `settings` (`key`, `value`)
    VALUES ('setup_closed_at', CAST(strftime('%s', 'now') AS INTEGER) * 1000);
END;
```

管理 API が受け付けるのは、ログインしていて、まだ `ADMIN_EMAILS` に入っていて、パスキーを持っているユーザーだけです。セットアップで得たセッションだけでは、最初のパスキーの登録しかできません。

## セッション [#sessions]

以前にトークンを知っていた別の人が、同じアドレスでセットアップを行い、そのセッションを持ち続けているかもしれません。次の決まりで、そうしたセッションが管理者のセッションにならないようにします。

- すでにユーザーがいるアドレスでセットアップをもう一度行うと、そのユーザーの以前のセッションを削除します。
- 最初のパスキーを登録するときは、パスキーを保存する前に、まずセットアップの完了を記録します。この記録は `setup_closed_at` がまだないときだけ書き込む 1 つのデータベース文で行うので、最初のパスキーの登録が同時に 2 つあっても、記録できるのは 1 つだけです。もう一方の登録は 403 になります。続けて、データベースにあるすべてのセッションを削除します。それまでにあるセッションは、セットアップで作ったものだけです。セットアップ画面は `createSession` を付けてパスキーを登録するので、パスキーより後に作られた新しいセッションが渡され、ログインしたままになります。
- 記録したあとでパスキーを保存できなかったときは、その記録を取り消すので、セットアップをやり直せます。取り消すのは、`setup_closed_at` がその登録の書き込んだ値のままで、パスキーが 1 つもないときだけです。
- セットアップは、セッションを作ったあとで、セットアップがまだ完了していないかをもう一度確認します。その間にパスキーの登録が完了を記録していたら、作ったセッションを削除して 403 を返します。
- セットアップが完了したあとは、パスキーを持たないユーザーはパスキーを登録できません。
- 最初のパスキーより前に作られたセッションは、管理 API が拒否します（401）。パスキーを追加で登録するときも同じセッションが必要なので、古いセットアップのセッションではパスキーを追加できません。

最初のパスキーを保存する直前に、パスキー登録のフックが次の処理をします。

```ts title="packages/server/src/features/setup/first-passkey.ts"
if (await isSetupClosed(db)) {
  throw new APIError('FORBIDDEN', { message: 'setup closed' });
}
const claim = await claimSetup(db);
if (!claim) throw new APIError('FORBIDDEN', { message: 'setup closed' });
claims.set(request, claim);
await getDatabase(db).delete(sessionTable);
```

完了の記録は `INSERT ... ON CONFLICT DO NOTHING` の 1 文です。行を書き込めた登録だけが先に進めます。

```ts title="packages/server/src/features/setup/setup-state.ts"
export const claimSetup = async (db: D1Database): Promise<string | null> => {
  const value = String(Date.now());
  const rows = await getDatabase(db)
    .insert(settings)
    .values({ key: SETUP_CLOSED_AT, value })
    .onConflictDoNothing()
    .returning({ value: settings.value });
  return rows.length === 1 ? value : null;
};
```

管理 API は、セッションの作成時刻を、そのユーザーの最初のパスキーの作成時刻と比べます。

```ts title="packages/server/src/features/auth/passkey-session.ts"
const first = await getDatabase(db)
  .select({ createdAt: passkey.createdAt })
  .from(passkey)
  .where(and(eq(passkey.userId, userId), isNotNull(passkey.createdAt)))
  .orderBy(asc(passkey.createdAt))
  .get();
if (!first?.createdAt) return 'no_passkey';
return sessionCreatedAt.getTime() < first.createdAt.getTime()
  ? 'too_old'
  : 'ok';
```

## セットアップ画面

管理者がいないサイトで `/admin/` を開くと、`/admin/setup` のセットアップ画面が出ます。手順は 3 つです。

1. **セットアップトークン。** `SETUP_TOKEN`、`ADMIN_EMAILS` に入っているメールアドレス、任意で名前を入力します。トークンの間違い、許可されていないアドレス、セットアップが完了済みであることは、それぞれ別のメッセージで知らせます。
2. **パスキー。** **パスキーを登録** を選びます。ブラウザ、スマートフォン、またはパスワード管理アプリがパスキーを作り、指紋・顔・PIN で確認します。画面には、パスキーが結びつくドメインを表示します。
3. **完了。** セットアップが完了し、管理画面が開きます。次回からは `/admin/login` でパスキーを使ってログインします。シークレットの `SETUP_TOKEN` はもう使わないので、ここで削除してください。

手順 1 のあとで画面を離れても、`/admin/setup` をもう一度開けば手順 2 から続けられます。

## なぜこう作るか

デプロイしたばかりのサイトは、持ち主がログインする前からインターネットに公開されています。セットアップ画面に最初に来た人が管理者になれるなら、先にサイトを見つけた知らない人に乗っ取られるおそれがあります。持ち主だけが知っているシークレットと、許可したメールアドレスの両方を求めることで、このすき間をふさぎます。作成後はセットアップを使えなくするので、`SETUP_TOKEN` が漏れても、後から管理者を増やされることはありません。

Cloudflare Access で `/admin/*`、`/api/setup`、`/api/auth/*` を守っていれば、Access を通った人しかセットアップにたどり着けません。`ACCESS_AUD` と `ACCESS_TEAM_DOMAIN` を設定すれば、Worker も `/api/setup` で Access のトークンを確認します。[セキュリティモデル](/ja/docs/security/#cloudflare-access)を参照してください。
