## 原則

- **フェイルクローズにします。** 必要な設定やシークレットが足りないときは、それを必要とする機能を止めます。`TURNSTILE_SECRET` がなければ、問い合わせ API は 503 を返します。
- **ログインなしで管理画面を開かせません。** 開発用の抜け道、既定のアカウント、共有のキーはありません。
- **問い合わせを失いません。** 応答の前に保存します。スパムの疑いがある問い合わせ（honeypot が埋まっている、スパムスコアが高い）も捨てずに保存し、別に表示します。
- **個人情報を Cloudflare の外に出しません。** 通知に個人情報を含めず、生の IP アドレスも保存しません。

## 管理画面

| 項目                           | 扱い                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ログイン                       | Better Auth のパスキー。メールとパスワードでのログインは無効です。パスワードのハッシュ処理は Workers 無料プランの CPU 上限を超えることがあります（[better-auth#8860](https://github.com/better-auth/better-auth/issues/8860)）。[パスキーでのログイン](/ja/docs/how-it-works/passkeys/)を参照してください。                               |
| セッション                     | 管理 API が受け付けるのは、そのユーザーの最初のパスキーと同時かそれより後に作られたセッションだけです。つまり、パスキーでのログインか、最初のパスキーの登録で作られたセッションです。セットアップで作られたセッションが管理者のセッションになることはありません。[セッションとセットアップ](#sessions-and-setup)を参照してください。      |
| `ADMIN_EMAILS`                 | リクエストのたびに読み直します。アドレスを外すと、そのセッションは次のリクエストから使えなくなります。[管理者を外す](#removing-an-admin)を参照してください。                                                                                                                                                                              |
| HTTPS                          | 管理画面、管理 API、セットアップ、ログインは `https://` でだけ動きます。[HTTPS](#https) を参照してください。                                                                                                                                                                                                                              |
| Cloudflare Access              | 強く推奨しますが、任意です。管理用のパスに Access のアプリケーションを設定します。たとえば Google のログインや、メールで届くワンタイムコードを使えます。50 ユーザーまで無料です。`ACCESS_AUD` と `ACCESS_TEAM_DOMAIN` を設定すると、Worker も Access のトークンを確認します。[Cloudflare Access](#cloudflare-access) を参照してください。 |
| 最初の管理者                   | `SETUP_TOKEN` と、`ADMIN_EMAILS` にあるメールアドレスが必要です。Access の 2 つの設定があるときは、正しい Access のトークンも必要です。最初のパスキーを登録するとセットアップは完了し、それ以降は使えません。[最初の管理者の作成](/ja/docs/how-it-works/first-admin/)を参照してください。                                                 |
| `workers.dev` とプレビュー URL | Access のポリシーから漏れやすいアドレスです。独自ドメインで動くようになったら無効にしてください。Access がなくても、管理画面にはパスキーでのログインが必要です。                                                                                                                                                                          |
| CSRF                           | `Origin` の確認と `SameSite` の Cookie で防ぎます。                                                                                                                                                                                                                                                                                       |
| ヘッダー                       | Worker の応答に Content Security Policy などのセキュリティヘッダーを付けます。どのヘッダーを付けるかはパスを正規化してから決めるので、`/%61dmin`、`//admin`、`/admin/..%2f` にも `/admin` と同じヘッダーが付きます。                                                                                                                      |

管理画面の外枠のページはセッションなしでも読み込めますが、データの取得には必ずセッションが必要です。

### セッションとセットアップ [#sessions-and-setup]

- すでにユーザーがいるアドレスでセットアップをもう一度行うと、そのユーザーの以前のセッションを先に削除します。
- 最初のパスキーを登録するとセットアップが完了し、データベースにあるすべてのセッションを削除します。ブラウザには、パスキーの登録そのものから、パスキーより後に作られた新しいセッションが渡されます。
- セットアップが完了したあとは、パスキーを持たないユーザーはパスキーを登録できません。セットアップのときのセッションが残っていても、別の管理者は作れません。
- 最初のパスキーより前に作られたセッションには、削除されずに残っていても、管理 API は 401 を返します。

### HTTPS [#https]

平文の HTTP では、セットアップトークン、セッションの Cookie、パスキーのやり取りが暗号化されずにネットワークを流れます。そのため、`/admin`、`/admin/*`、`/api/admin/*`、`/api/setup`、`/api/auth/*` では次のようにします。

- `http://` での `GET` と `HEAD` は、同じ URL の `https://` にリダイレクトします（308）。
- `http://` でのそれ以外のメソッドには、コード `https_required` の 403 を返します。本文はもう送られてしまっているので、リダイレクトはしません。
- `wrangler dev` のために、`localhost`、`127.0.0.1`、`[::1]` は対象外です。

サイトと問い合わせフォームには影響しません。これらも守るには、ゾーンの **Always Use HTTPS** を有効にしてください（Cloudflare ダッシュボード > SSL/TLS > Edge Certificates）。

### Cloudflare Access [#cloudflare-access]

Access のアプリケーションは次のパスに設定します。

- `/admin` と `/admin/*`
- `/api/admin/*`
- `/api/setup`
- `/api/auth/*`

`/api/contact` は公開したままにしてください。訪問者は問い合わせフォームからここに送信します。

次の 2 つの設定が両方あるとき、Worker は同じパスで `Cf-Access-Jwt-Assertion` ヘッダーを確認します（[Cloudflare: JWT の検証](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)）。確認するのは、`https://<チームドメイン>/cdn-cgi/access/certs` の鍵による RS256 の署名（鍵は Worker が 1 時間キャッシュします）、発行者、aud、`exp`、`nbf` です。

| 設定                 | 値                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| `ACCESS_AUD`         | Access アプリケーションの **Application Audience (AUD) Tag**。カンマで区切って複数指定できます。 |
| `ACCESS_TEAM_DOMAIN` | チームドメイン。たとえば `your-team.cloudflareaccess.com` です。                                 |

- トークンがない、または正しくないときは 403（`access_denied`）を返します。
- 2 つの設定の片方だけがあるとき、`ACCESS_TEAM_DOMAIN` がホスト名だけの形になっていないとき、または鍵を取得できないときは、これらのパスは 503（`access_unavailable`）を返します。
- どちらの設定もなければ、Worker は Access のトークンを確認しません。サイトの前の Access はそのまま働きます。Worker が二重に確認しないだけです。
- Access を使っていても、パスキーでのログインは必要です。

### 管理者を外す [#removing-an-admin]

Worker は `ADMIN_EMAILS` をリクエストのたびに読みます。アドレスを外すと、そのセッションは次のリクエストから 403 になり、パスキーでログインし直しても使えません。

ただし、ユーザー、セッション、パスキーは D1 に残ります。あとで同じアドレスを戻すと、また使えるようになります。削除するには、次のコマンドを自分で実行してください（アドレスは置き換えます）。

```sh
npx wrangler d1 execute DB --remote --command "DELETE FROM session WHERE user_id IN (SELECT id FROM user WHERE email = 'old@example.com'); DELETE FROM passkey WHERE user_id IN (SELECT id FROM user WHERE email = 'old@example.com'); DELETE FROM account WHERE user_id IN (SELECT id FROM user WHERE email = 'old@example.com'); DELETE FROM user WHERE email = 'old@example.com';"
```

これでセットアップがまた使えるようになることはありません。`settings.setup_closed_at` は残ります。

## 問い合わせフォーム

- Turnstile はサーバー側で検証し、`hostname` と `action` も確認します。
- 本文を読む前に、`Origin`、`Content-Type`、本文のサイズを確認します。
- honeypot 欄が入力されていても、応答は変えません。その送信も Turnstile と回数制限と検証を通す必要があり、通ればスパムの疑いとして保存します。honeypot 欄の値そのものは保存しません。
- スパムスコアが高い送信には、スパムの疑いの印を付けます。スパムの疑いがある送信は Slack に通知せず、管理画面では別に表示します。
- Rate Limiting binding で、`ip_hash` ごとに送信回数を制限します。
- ページに API キーを入れません。ブラウザが読めるキーは秘密ではないので、守っているという誤解を生むだけです。

[問い合わせフォームの保護](/ja/docs/how-it-works/contact-protection/)を参照してください。

## SQL インジェクション [#sql-injection]

サーバーは、入力を SQL の文字列に入れません。

- すべてのクエリで [Drizzle ORM](https://orm.drizzle.team/) のクエリビルダーを使います。管理画面の一覧の件数とオフセットも含めて、値はバインドされたパラメーターとして D1 に送ります。
- URL から来る数値は、クエリに渡す前にルートで確認します。`page` は 1 から 100,000、`limit` は 1 から 100 で、数字だけで書かれている必要があります。`1; DROP TABLE submissions`、`-1`、`1e9`、`50 OFFSET 0` のような値には 400 を返します。
- 生の SQL は Drizzle の `sql` テンプレートでだけ書けます。このテンプレートも値をバインドします。サーバーのコードが `sql.raw()` や D1 の `prepare()` を直接呼んだり、Drizzle の `$client` で D1 の binding に触れたりすると、CI のチェックが失敗します（`bun run check:sql`。[データベース](/ja/docs/database/#how-queries-are-written)を参照）。
- メールアドレスの検索では、`%`、`_`、`\` をエスケープし、パターンを 1 つのバインドされたパラメーターとして `ESCAPE '\'` 付きで送ります。
- テストでは、一覧の API にインジェクション用の文字列を送って 400 になることを確かめます。また、データベースに送った文を記録して、入力がパラメーターにだけ現れることを確かめます。

```ts title="packages/server/src/features/admin-api/admin-query.ts"
const boundedInteger = (max: number) =>
  z
    .string()
    .max(String(max).length)
    .regex(/^[1-9][0-9]*$/)
    .transform(Number)
    .pipe(z.number().int().min(1).max(max));
```

```ts title="packages/server/src/features/admin-api/admin-query.ts"
export const listQuerySchema = z
  .strictObject({
    ...filterShape,
    dir: z.enum(['asc', 'desc']).default('desc'),
    page: boundedInteger(ADMIN_MAX_PAGE).default(1),
    limit: boundedInteger(ADMIN_MAX_PAGE_SIZE).default(ADMIN_PAGE_SIZE),
  })
  .refine(bothOrNeither);
```

`filterShape` には、`view`（`unread`、`read`、`all`、`spam`）、`q`（メールアドレスの検索。254 文字まで）、バージョンと選択肢の絞り込みがあり、それぞれ zod のスキーマを持ちます。続いて、ストアが Drizzle でクエリを組み立てます（[データベース](/ja/docs/database/#how-queries-are-written)を参照）。`?view=unread&q=50%_off&page=3` のとき、テストで使う記録用の D1 には、次の文とパラメーターが届きます。

```sql
select "id", "created_at", "email", "status", "suspected_spam", ... from "submissions"
where (("submissions"."status" = ? and "submissions"."suspected_spam" = ?)
  and lower("submissions"."email") like ? escape '\')
order by "submissions"."created_at" desc, "submissions"."id" desc
limit ? offset ?
```

```json
["unread", 0, "%50\\%\\_off%", 50, 100]
```

SQL の文字列は、検索する文字、ページ、件数が何であっても同じです。変わるのはパラメーターだけです。[データベース](/ja/docs/database/)を参照してください。

## シークレット

- シークレット（`SETUP_TOKEN`、`ADMIN_EMAILS`、`BETTER_AUTH_SECRET`、`IP_HASH_SECRET`、`TURNSTILE_SECRET`、`SLACK_WEBHOOK_URL`）はすべて Worker のシークレットに置きます。
- `SETUP_TOKEN`、`BETTER_AUTH_SECRET`、`IP_HASH_SECRET` は 32 文字以上にしてください。短い値は設定されていないものとみなされ、それを使うセットアップ、ログイン、問い合わせフォームが 503 を返します。セットアップが完了するまでは、`GET /api/setup` が足りない設定や短すぎる設定の名前を返します（値は返しません）。`IP_HASH_SECRET` が短すぎるときは、管理画面にも表示します。
- セットアップが終わったら `SETUP_TOKEN` は削除してください。もう使いません。
- ブラウザに返すことも、D1 に書くこともありません。Slack の Webhook URL は管理画面にも表示しません。
- 管理画面に更新ボタンはありません。あなたの GitHub リポジトリに書き込めるトークンが必要になるからです。

## CSV の書き出し

- 1 回のクエリで 200 行ずつ読み、順に送り出します。表が大きくても、1 つのファイルとして Worker のメモリに載ることはありません。
- 空白を除いた最初の文字が `=`、`+`、`-`、`@` のセルと、タブや復帰文字で始まるセルには、先頭に `'` を付けます。表計算アプリは、それを数式として実行せずに文字として表示します。

## 更新とリポジトリ

- 修正は Dependabot の PR で届きます。公式アップデートのコメントが付いた PR だけをマージしてください。[配布と更新のしくみ](/ja/docs/distribution/)を参照してください。
- リポジトリは private にしてください。public の間は、starter の公開範囲チェックが失敗します。
- goodnight-web は、それ自体の依存関係を少なくし、バージョンを固定しています。

## 守れないもの

- あなたの Cloudflare アカウントや GitHub リポジトリに入れる人が行うこと。
- あなたのパスキーが入った端末を、ほかの人が使うこと。
- 公式アップデートではない PR をマージすること。
- あなたがサイトに載せる内容と、starter に加えた変更のコード。
- Turnstile と回数制限をすり抜けるスパム。honeypot とスパムスコアで多くにスパムの疑いの印を付けますが、通常の一覧に届くものもあります。

## 脆弱性の報告

脆弱性は GitHub Security Advisories で非公開に報告してください。goodnight-web リポジトリの **Security** タブを開き、**Report a vulnerability** を選びます。公開の Issue には書かないでください。
